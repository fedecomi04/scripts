# RUNTIME TRIAGE — adversarial-refutation verdicts

**Tally: 28 CONFIRMED / 17 REFUTED / 2 UNCERTAIN** (47 hazards triaged)

**Bottom line:** the audit over-flagged. Of 28 "confirmed" hazards, **only 4 are medium and ZERO are high** in the shipped live config — the rest are low/none (benign races behind the GIL, perf notes, doc staleness, or shutdown-only leaks that self-heal on next launch). Almost every "high/medium" original rating was knocked down because the dangerous-looking gauss_params tears all actually happen under `_model_lock`, and the scariest latent tear (`_pick_d0_object` unlocked read) is unreachable in the default config (picker off, FF gated off while `is_first`). The 4 mediums are real correctness/robustness gaps but none crash or corrupt in normal operation; two of them (H4/H4-dup pose skew) are the SAME already-documented-and-accepted FF/CDN frame-seam, and one (ff-dispatch H1 crop read) is a genuine narrow-window crash on the hot path worth a one-line lock. Spend review time on the 3 below; skim the rest.

## TOP 3 CONFIRMED (highest severity)

1. **`live_ros_publisher.py:751-781` (shm H3) — MEDIUM — the one true corrupting unguarded race.** `_on_joint_state` and `_on_gazebo_pose` are TWO independent `rospy.Subscriber` objects (`:644-648`), each with its own receive thread, both writing the pose/joint history lists with NO lock while the worker thread reads them in `_interpolate_c2w`. The two-statement `times.insert`/`mats.insert` (`:780-781`) is interruptible → reader can observe `len(times)!=len(mats)` → IndexError or wrong interpolated pose. "Hasn't blown up" = GIL + 20 ms throttle luck, not correctness.
2. **`dynamic_gs_pipeline_base.py:1866-1876` (ff-dispatch H1) — MEDIUM — narrow-window crash on the live hot path.** Live default `xfeat_crop_to_object_bbox=True`, so `_object_crop_bbox` runs every tick on the main tracker thread with no `_model_lock`. The guard at `:1874` reads `n_means` at `:1873`, but `model.means[obj_mask]` at `:1876` re-reads the means Parameter; an FF insert reassigning means (`model.py:1219`) in that gap leaves new-N means indexed by old-N mask → size-mismatch crash that kills the tracker thread (no try/except at the `:2083` call site). One-line lock wrap closes it.
3. **`dynamic_gs_pipeline_live.py:323/465` (ff-dispatch H4 ≡ tracker H1 ≡ warmload H2 ≡ shm H5) — MEDIUM — FF places inserts against a newer pose than the CDN scored.** `_scene_c2w_for_frame` reads `self._latest_tracker_frame['camera']` LIVE (`live:465`), not the `target_frame` the FF was dispatched with; main re-points that attribute every tick during the ~200 ms FF run → inserts back-projected with a later camera than the depth/CDN they were selected from → mm-cm drift feeding CDN churn. Correctness drift, not a crash. NOTE: this is on top of the already-documented + operator-accepted ICP/frame seam (ICP kept ON).

## 3) UNCERTAIN — YOU DECIDE (2)

- **`dynamic_gs_pipeline_live.py:367,381,398 + dynamic_gs_model.py:1216-1228 (tracker H2)`** — `_pick_d0_object` reads `model.means`/`object_instance_ids` UNLOCKED while the N-growing Parameter realloc would tear it. Both the unlocked read and the realloc are genuinely real (NOT refutable as safe code). It is unreachable in the *default* config: `_pick_d0_object` runs only at `is_first`, and `_recurring_ff_due` returns False while `is_first` (`base:950-951`), so no FF thread can be inserting; the mid-run reselect path that would expose it is gated by `interactive_object_selection=False` (no override in the live config / bootstrap / resume scripts).
  - **Open question:** is the picker / mid-run object switch ever going to be enabled in a real live run, OR will a future change remove the `is_first` FF gate?
  - **Settles it:** if yes to either → this becomes a real **HIGH-severity** tear (new-N means indexed by old-N mask). A one-line `_model_lock` wrap around the `_pick_d0_object` reads fixes it unconditionally and is cheap insurance regardless of intent. **Recommend wrapping it now.**

- **`dynamic_gs_pipeline_base.py:1695-1702 + dynamic_gs_model.py:2219,2223,2268,2336,2346 (viser H1)`** — `model.train()/eval()` flipped outside the lock while the viser render thread reads `self.training` inside `get_outputs`. The unsynchronized cross-thread read of the global `self.training` bool IS real and unguarded. But in the LIVE config every consuming branch is inert: `render_mode=RGB+ED` regardless (`output_depth_during_training=True`), `camera_optimizer` gated on `phase=='static'` (live is `'dynamic'`), `use_bilateral_grid=False`, `crop_box` always None. A torn read changes nothing the viser path reads (only `outputs['rgb']`).
  - **Open question:** will `use_bilateral_grid` ever be turned on, or will this code path ever run in `phase=='static'`?
  - **Settles it:** if either becomes true, a torn `self.training` read would silently mis-apply (or skip) bilateral / camera-opt during a render. Today: zero visible effect. Marked uncertain (not refuted) because the race exists and a config flip would make it bite. Low priority unless those flags are planned.
